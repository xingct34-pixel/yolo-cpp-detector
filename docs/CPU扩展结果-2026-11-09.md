# CPU扩展结果

日期为2026-11-09，环境为WSL Ubuntu 24.04、i5-9400、OpenCV C++ 4.6、ORT 1.21.1 CPU。未隔离Windows背景负载和系统页缓存。

## 自动化及端到端验收

- Release CTest 10/10通过，含可选量化预处理3个Python单元场景，以及C++外部缓冲逐元素对照。
- ASan/UBSan CTest 9/9通过，预编译ORT/OpenCV未进行同等插桩。
- 原FP32改动前、改动后、INT8三种路径均通过真实C++视频16帧回归，读取/推理/输出一致。
- INT8模型通过ONNX checker及FP32输入输出合同检查，检查帧输出全部有限。

## 静态INT8 QDQ

FP32模型10,741,398字节，生成模型3,190,029字节，约减少70.3%。仅选择Conv/MatMul进行QDQ量化，保留浮点输入输出与未量化算子。

原模型SHA-256为 `128aa171b8f0172c6c65d65b94cb1cc9d4adb965e31514083f3004bd4e1f94cd`。

INT8模型SHA-256为 `a8a2685c9d5bbdf8afa762fbfee5b537637cf491b64ae8922f090b7450e25f12`。

8个校准帧仅包含5种不同输入张量，8个检查帧仅有4种，二者存在1种相同内容。该视频可用于流程回归，不能用于独立检测精度验证。mAP未评估，原始张量/分数误差不替代mAP。

固定3个CPU线程、各2次预热、8个检查帧×3轮交替测量，Python Session.run中位耗时为FP32 65.11ms、INT8 100.32ms。本轮量化模型更小，但在该机器及工作负载下更慢，不作为加速成果。

## 原生C++交替测量

从修改前Git HEAD导出源码，在独立临时目录重新构建基线。顺序模式，每例16帧、预热2帧、3线程。每轮反转执行顺序，VmHWM采样间隔20ms。单位为KiB。

|轮次|路径|FPS|进程峰值RSS采样|
|---|---|---|---|
|0|改动前FP32|10.20|232812|
|0|改动后FP32|13.95|233180|
|0|INT8|9.05|237464|
|1|INT8|9.15|237496|
|1|改动后FP32|14.21|233188|
|1|改动前FP32|13.25|233428|

改动后FP32在本轮两次测量中FPS较高，但样本少且预处理耗时波动明显，不推广为稳定加速比。进程峰值RSS没有显示一致下降，不把结构上减少4.69MiB临时张量等同于实测RSS下降。

# 从一次视频处理理解工程

固定学习版本后，按 `main.cpp → Pipeline → ThreadSafeQueue → Detector → OrtBackend` 阅读，最后看纯处理函数及测试。

## 资源与线程

模型在 Detector 构造时加载一次，推理线程独占 Detector。读取线程解码帧并把拥有像素数据的 Mat 送入队列；推理线程预处理、运行模型、后处理；主线程消费结果。线程异常保存在 exception_ptr 中，关闭两个队列、唤醒生产者和消费者，join 后由主线程报告。信号处理器只设置 lock-free 原子标志，监视线程完成实际关闭。

默认 block 策略用于离线视频：队列满时生产者等待，正常读完后逐级排空，不丢帧。drop-oldest 用于优先新鲜度的实时风格输入：丢弃最旧数据，并统计丢帧。视频文件以最快速度读取，不模拟摄像头帧率；丢帧实验不能代表真实摄像头负载。

## 一帧的处理

1. 等比缩放并补边，记录实际横纵缩放比例和左上 padding。
2. `blobFromImage` 完成 BGR→RGB、归一化和 HWC→CHW。
3. 用已有 buffer 创建 ORT Tensor；buffer 必须活到 Run 返回。
4. 接收固定形状 `[1,84,8400]`，过滤无效坐标和低置信度候选。
5. 撤销 padding 与实际缩放，裁剪到原图边界，按类别分别 NMS。
6. 绘制结果并输出；图片模式另可输出结构化框信息。

## 面试与自测

- 为什么模型不在每帧中加载？
- 为什么关闭队列要通知两种等待者？为什么 wait 需要谓词？
- 完整处理视频和优先实时新鲜度为何需要不同队列策略？
- 为什么吞吐提升可能伴随更高的排队延迟？
- 为什么不能把不同类别的框相互抑制？
- Letterbox 取整如何影响坐标还原？
- 为何端到端帧延迟不包含模型初始化，但实验总时间又可能包含它？

建议独立重写一个支持 close 的有界队列，再改变容量运行同一视频。先提出预测，再用 JSON 报告检验；不要通过代码行数判断是否掌握。
